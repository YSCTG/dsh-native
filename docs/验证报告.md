### 缓存：我错了两次，第三次才对

| 版本 | 结论 | 错在哪 |
|---|---|---|
| 初稿 | 缓存护住全部上下文，500K 历史每轮 ≈ $0.003 | 方向对，但当时没数据支撑 |
| 第二版 | 只有头部缓存，历史全价，500K 每轮 ≈ $0.15 | **测试退化**：每轮只输出 1 token，推不动缓存单元 |
| 定稿 | 历史逐轮累积，单元按 128 token 对齐 | —— |

第二次的测试（`LiveScaleTest`，头部 1841 token）：四轮命中量恒为 1664，看起来像"历史不吃缓存"。
但那个测试每轮只回一个字，128 token 的缓存块根本没被推过去。

第三次（`LiveHistoryTest`，6 轮，每轮输出约 150 token）才看清真相：

| 轮 | in | 命中 | 未命中 | 命中率 | 命中增量 |
|---|---|---|---|---|---|
| 1 | 737 | 0 | 737 | 0.0% | +0 |
| 2 | 1420 | 1280 | 140 | 90.1% | +1280 |
| 3 | 1591 | 1408 | 183 | 88.5% | **+128** |
| 4 | 1752 | 1536 | 216 | 87.7% | **+128** |
| 5 | 1911 | 1664 | 247 | 87.1% | **+128** |
| 6 | 2064 | 1920 | 144 | 93.0% | +256 |

- **历史确实被缓存，逐轮累积**，命中增量恒定是 **128 的整数倍**（缓存单元按 128 token 对齐）
- **每轮全价的只是一条尾巴**：未命中稳定 140–250 token，与历史总长无关
- 500K 历史每轮 ≈ 500K × $0.006/M + 250 × $0.30/M ≈ **$0.003** —— 初稿估算成立

真机数据也对得上：三轮会话命中率 77% → 91% → 85%，历史越长命中越高。

**所以「追加为主、默认不压缩」是对的；唯一会烧钱的操作是改头部。**
初稿结论侥幸对了，但推理过程是错的——如果当时照第二版去写压缩器，会白做一层没人需要的东西。

## 6. Keystore（真机 + 模拟器磁盘级）

API key 从明文 SharedPreferences 搬进 **AndroidKeyStore + AES-256-GCM**（项目零依赖，直接用平台 JCE）。
密钥生成在 Keystore 里、不可导出，落盘格式自己定：`base64(iv) + ":" + base64(密文)`。

真机（华为，非 root）验的是**迁移 + 解密往返**：
装上新版后，老明文 key 被就地加密，账本从「就绪」变成「就绪 · key 已加密（Keystore）」，
随后一轮真 API 正常返回——说明密文能被 Keystore 里的密钥解回来。

磁盘级证明只能在能 `adb root` 的模拟器上做，用一条金丝雀字符串当 key，然后直接看文件：

```xml
<map>
    <string name="base_url"></string>
    <string name="api_key_enc">KYSkyQPejXsMwOu9:Vq1f+/BDeO8FIs5ECXXndj+GKfGUcTHY7YDkeVzqRsG5/Sa7AfJ1EA==</string>
</map>
```

- ✅ 磁盘上搜不到金丝雀明文
- ✅ 只有 `api_key_enc`（IV + GCM 密文）
- ✅ 旧的 `api_key` 明文条目已被删除

降级策略：Keystore 建不出来才退回明文，并且界面上会写「key 为明文（Keystore 不可用）」——
宁可让人看见没加密，也不假装加密了。

## 验证过程中打出来的 6 个真 bug



这就是"在真机上跑一遍"的价值——前三个是设计层面的，编译和 JVM 测试都发现不了：

1. **base URL 预填导致拼接**：对话框里预填了官方地址，自动化 `input text` 追加成
   `https://api.deepseek.comhttp://10.0.2.2:8899` → `Unable to resolve host`。
   改成**留空即默认**，顺带对用户也更省事。
2. **先 force-stop 再开无障碍 = 服务被永久标 crashed**：系统会把它记进 `Crashed services`
   并清掉设置，之后再也不绑。正确顺序是**先让 App 活着，再改 secure settings**。
3. **会话中途开无障碍，旧会话拿不到 `ui_*`**：工具清单是冻结的（这是故意的），
   但缺了"新增能力后开新会话"的路径。补了 `onNewIntent`，让 `am start --es prompt` 能在已运行的实例上再喂一条。
4. **`ui_dump` 的结果不上屏**：工具回灌给模型的正文本来就不该进对话区，
   但"这次读到多少"应该看得见。工具卡现在显示 `[ui_dump 10 节点]`。
5. **Android 的 `org.json.optString` 把 JSON null 变成字面量 `"null"`**（真机才暴露）：
   真 API 的流式 delta 里带 `"content": null`，`optString(key, "")` 返回的不是空串而是 `"null"`，
   于是正文被灌成一串垃圾：`nullDirectorynull isnull emptynull...`。
   mock 从不发 `null` 字段，所以 JVM 17 项全绿也抓不到。改成显式 `isNull()` 判空才修好。
   **这条是"必须打真 API"的最有力证据。**
6. **折叠后的思考卡一碰就崩**（真机操作时打出）：`finishThinking()` 把 `thinkingBody` 置空，
   但那个卡片仍留在对话流里、仍然可点 → `NullPointerException`（`MainActivity.java:430`）。
   改成点击时在视图树里找 `body`，不依赖会被清空的字段。连点两次验证不再崩。

另外两个环境坑（不是代码问题，但会卡住任何人复现）：
- 沙箱禁止子进程写 `%TEMP%` → adb server 起不来。解法：`TMP`/`TEMP`/`ANDROID_EMULATOR_HOME` 全指进工作区（见 `tools/env.ps1`）。
- 沙箱禁止模拟器写 `C:\Users\<u>\.android\` → 锁文件 access denied、刷 389 MB 日志。解法：AVD 也放进工作区。
