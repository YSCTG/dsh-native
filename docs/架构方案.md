# DSHS —— 原生手机版 Harness 架构方案

> deepseek harness of smartphones。目标：一个 APK，一个 API key，在**无 root** 的手机上
> 像电脑版 DSH 一样行动（读写文件、操作界面、驱动其他应用），界面简洁，插件可自装，
> **不需要再装任何第二个 App**。
>
> 现状约束（本工作区已验证）：JDK 17 + Android SDK build-tools 34 + platform android-35 已就位，
> 手工 `aapt2 → javac → d8 → zipalign → apksigner` 链路可用（`dsh-mobile/build-apk.ps1` 已在跑），
> 无 Gradle、无 AndroidX、无 adb/真机在线。

---

## 0. 一句话结论

**不要把电脑版 DSH 搬到手机上，要移植它的"契约"。**

Cordis 插件树是 Node 运行时，在手机上必死（你已经用 `ext2..ext5` 试过四次了）。
真正值得移植、而且手机上能跑的是三样东西：

1. **工具 schema 的形状**（name / description / JSON Schema / 只读-破坏性标注）
2. **插件清单的语义**（bundle = 清单 + 工具 + skill 文本 + 可选代码 + slot）
3. **agent 循环的语义**（append-only 事件流、工具结果回灌、可中断）

执行体用 Java 重写。**手机权限做成"命名能力"，不做成裸 shell。**

## 1. 三条不可协商的物理约束（先看这个，它决定一切）

### 约束 A：DeepSeek 的缓存是「整段前缀单元全匹配」，命中价是未命中的 2%

官方文档（[KV Cache](https://api-docs.deepseek.com/guides/kv_cache)、[Price](https://api-docs.deepseek.com/quick_start/pricing)）：
缓存默认开启、无需改代码；`deepseek-flash` 命中 $0.006/M、未命中 $0.30/M、输出 $1.20/M（峰时，谷时减半）。
命中要求**某个前缀单元被完整匹配**，不是最长公共前缀：

```
A+B     →  A+B+C     命中 A+B        （追加：命中）
A+B     →  A+C       全部 miss        （改写：归零，无部分抵扣）
```

**推论（这是本方案最重要的一条）：**

- 上下文必须 **append-only**。任何"就地改写历史"（包括压缩摘要）都会让整段归零。
- **时间、路径、电量、模型名、待办列表，绝不能放进 system prompt**。放进去 = 每轮前缀都变 = 永远 miss。
  易变状态要么交给工具让模型去问，要么贴在**最新一条 user 消息的尾部**（尾部之后的内容还没进缓存，改了不亏）。
- **工具清单在一个会话内必须冻结**。加一个工具 = 改前缀 = 全量 miss。
  技能（skill）是**追加**进历史里的，所以安全；工具 schema 不是。
- 每一轮必须把 `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 记下来并显示。命中率掉到 0 = 代码里有人在改写前缀。

### 约束 B：缓存按 128 token 对齐、历史逐轮累积（三次实测后定稿）

`deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 下线，现役是 `deepseek-flash` 与 `deepseek-v4-pro`，
**1M 上下文、384K 输出**。

这一条我前后错了两次，第三次才测对。**过程本身比结论更有用**，所以把三次都留着：

| 版本 | 结论 | 错在哪 |
|---|---|---|
| 初稿 | 缓存全护住，500K 上下文每轮 ≈ $0.003，不用压缩 | 结论方向对，但没数据 |
| 第二版 | 只有头部缓存，历史全价，500K 每轮 ≈ $0.15 | **测试退化**：每轮输出只有 1 token，推不动缓存单元 |
| 定稿 | 历史逐轮累积，按 128 token 对齐；每轮全价的是尾巴 | —— |

定稿实测（`tools/test/LiveHistoryTest.java`，6 轮，每轮输出约 150 token）：

| 轮 | in | 命中 | 未命中 | 命中率 | 命中增量 |
|---|---|---|---|---|---|
| 1 | 737 | 0 | 737 | 0.0% | +0 |
| 2 | 1420 | 1280 | 140 | 90.1% | +1280 |
| 3 | 1591 | 1408 | 183 | 88.5% | **+128** |
| 4 | 1752 | 1536 | 216 | 87.7% | **+128** |
| 5 | 1911 | 1664 | 247 | 87.1% | **+128** |
| 6 | 2064 | 1920 | 144 | 93.0% | +256 |

真正的规则：

- **命中量随历史逐轮增长**，增量恒定是 **128 的整数倍** —— 缓存单元按 128 token 对齐
- **每轮全价的只有尾巴**：未命中稳定在 140–250 token，与历史总长无关
- 所以 500K 历史每轮 ≈ 500K × $0.006/M + 250 × $0.30/M ≈ **$0.003/turn** —— 初稿的估算是对的
- 真机实测也吻合：三轮会话命中率 77% → 91% → 85%，且历史越长命中越高

**所以策略回到「追加为主」，但有三条纪律：**

1. **头部必须冻结**（system + 工具 schema）。改一个字节，之后所有 128 块全部作废——这是唯一会烧钱的操作。
   工具 schema 因此可以给得大方。
2. **追加是安全的**，历史会被吃掉，成本近乎线性于"新增内容"而不是"总长度"。
3. **压缩是为了窗口和延迟，不是为了省 token**。真压的时候那一次是全量 miss（几十万 token 一次计价），
   要给出预估金额并要人确认；压完之后的轮次继续正常累积。

补充事实：带 `tools` 时，**所有历史轮的 `reasoning_content` 必须原样回传**，否则 400。
它是 token 大户，且会随历史累积——正好被缓存吃掉，但必须显示它占了多少。思维模式下
`tool_choice=required/指定某函数` 会 400，移动端一律 `auto`。

### 约束 C：targetSdk ≥ 29 不能在 app 私有目录 exec 自己带的 ELF

SELinux 的 `untrusted_app` 域对 `app_data_file` 没有 `execute_no_trans`
（[Android 10 行为变更](https://developer.android.com/about/versions/10/behavior-changes-10)）。
14/15/16 一脉相承，**按 targetSdk 触发，不按系统版本触发**。逐位置结论（已核实）：

| 位置 | 能否 exec |
|---|---|
| `filesDir` / `cacheDir` / 外部私有目录 | ❌（ELF 和 shebang 脚本都不行） |
| **native lib 目录**（`extractNativeLibs=true` → `nativeLibraryDir`） | ✅ 官方指定的可执行位置，`System.loadLibrary`/`dlopen` 一直可用 |
| `/data/local/tmp` | 属 shell(uid 2000)，普通 app 连写都不行，需 Shizuku/root |
| `/system/bin/sh -c …` | ✅ 禁的是 exec **自己目录里的文件**，不是拉起系统二进制 |

所以工具实现的路数：

- 优先**原生 Java 字节码**；真要跑外部二进制，打包成 `.so` 放 `jniLibs`，从 `nativeLibraryDir` exec
- 或走 `su` / Shizuku（uid 2000）代跑
- `su -c` 每次冷启动约 100–300ms，P1 换成 **libsu 的持久 shell**
- 「打包 node 当主进程」不是做不到，是**不该做**：要么把 targetSdk 停在 28，
  要么靠 `/system/bin/linker64 <abs path>` 这种非公开、机型相关的偏门
  （Shelly 就是这条路，作者自己标注 N=1）

**一个真正值得权衡的开关：targetSdk 28。** Android 15/16 的最低可安装 targetSdk 是 **24**，
所以 28 既能装、又保留 app 私有目录的 exec 权。代价是无 scoped storage、Play 无法上架、Play Protect 提示。
换来的是：**手机上能跑真正的解释器**（bash / python / node），
于是 **stdio 型 MCP server** 变得可行——这对插件生态是数量级的差别（MCP server 大多就是 node/python 子进程）。
本方案默认取 **34**（语义现代、够用），这个开关留到 P2 再定。

## 2. 对现有 `dsh-mobile` 的诊断（为什么它不是答案）

| 项 | 现状 | 问题 |
|---|---|---|
| 形态 | 32KB WebView 外壳 | 手机只是显示器 |
| 后端 | 网关 :3080 → PC 上的 `dsh web` :3081 | **电脑必须常驻开机** |
| 同步 | 共用 `~/.dsh` 会话库 | README 自己写了：电脑上正在跑的那一轮**不实时镜像** |
| 手机能力 | 无 | 模型完全碰不到手机的文件、应用、系统 |
| 认证 | URL 里的 `token=` 即钥匙，cookie 绑 Host | 链接泄露＝电脑沦陷；你的 README 也警告了 |

它解决的是"远程连到电脑"，不是"手机上的 DSH"。**保留它**（出门在外连家里那台很实用），
但新 App 是独立的东西：本地执行、本地会话、本地工具。两者可以**共享工作区目录格式与会话文件格式**，
不要共享进程。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│ L5 UI        Compose/View：对话流 · 工具卡 · token 账本 · 权限徽章 │
├──────────────────────────────────────────────────────────┤
│ L4 插件      .dshp 包（清单+工具+skill+可选 dex）· MCP 客户端      │
├──────────────────────────────────────────────────────────┤
│ L3 Agent     会话事件流(append-only) · 循环 · 中止 · 缓存账本      │
├──────────────────────────────────────────────────────────┤
│ L2 工具      typed tools：fs.* · phone.* · pkg.* · net.* · sh    │
├──────────────────────────────────────────────────────────┤
│ L1 权限中介  CapabilityBroker：策略引擎 · 审计 · 确认 UI          │
├──────────────────────────────────────────────────────────┤
│ L0 运行时    前台服务 · WakeLock · Keystore · 崩溃可恢复的会话      │
└──────────────────────────────────────────────────────────┘
         ↓ 能力落点
   root(su) │ Shizuku(uid2000) │ 无障碍服务 │ 普通 App 权限
```

### L1 权限中介 —— 本方案的安全核心

**模型永远看不到 "root"。它只看到能力名。** 由 broker 决定用哪一档去兑现。

约束条件是**无 root、不装第二个 App**，所以档位表按"手机上真的能拿到什么"重排：

| 档 | 怎么来的 | 拿到什么 | 拿不到什么 |
|---|---|---|---|
| **APP** | 普通运行时权限 | 自己工作区文件、`MANAGE_EXTERNAL_STORAGE` 下的共享存储、剪贴板、通知、`QUERY_ALL_PACKAGES` 列应用、Intent 拉起应用 | 改系统设置、装卸应用、往别的 App 里点 |
| **A11Y** | 系统设置里打开无障碍服务 | 读任意界面的节点树、`dispatchGesture` 点击滑动 | 没有 shell、读不到别家 `/data` |
| **ADB** | **App 自己内置的 ADB 自举**（无线调试配对 → 连 127.0.0.1 → `app_process` 起 uid 2000 通道） | `pm`/`am`/`settings`/`input`/`dumpsys`/`screencap`，即"快而稳"的系统操作 | 每次重启要重新配对；仍读不到别家 `/data` |
| **ROOT** | 有就用 | 一切 | —— |

**关键：A11Y 档已经足够让 App 独立完成任务。** 这是"无 root + 不装别的"能成立的原因——
装卸应用可以 `ACTION_VIEW` / `ACTION_DELETE` 拉起系统安装器，再用无障碍点"安装"；
改设置可以驱动设置界面。慢，但不需要任何特权。

**ADB 档是加速器，不是前提。** 它把"驱动界面"换成直接的 `pm`/`settings` 调用，三步变一步。
它必须由 App 自己实现配对，否则就要装 Shizuku——那违背约束。

**代价必须说清楚**：无线调试重启后默认关闭，用户每次开机要进 App 点一次"重新配对"（约 30 秒）。
这不是"一次配置永久生效"，是"每次开机一次"。部分国产 ROM 还会限制无线调试配对。
所以 **ADB 档永远可选，缺了它整个 Agent 依然可用**。

| 能力 | 首选档 | 兜底档 | 默认策略 |
|---|---|---|---|
| `fs.read` / `fs.write`（工作区） | APP | —— | auto / **confirm** |
| `fs.read`（共享存储） | APP（需「所有文件访问」授权） | —— | auto |
| `app.list` | APP | A11Y（驱动设置页） | auto |
| `app.launch` | APP（Intent） | A11Y | auto |
| `pkg.install` / `pkg.uninstall` | ADB | **A11Y 驱动系统安装器** | **confirm** |
| `sys.settings` | ADB | **A11Y 驱动设置界面** | **confirm** |
| `ui.read` | A11Y | —— | auto |
| `ui.act` | A11Y | —— | **confirm** |
| `screen.capture` | MediaProjection | —— | **confirm**（每会话授权） |
| `clip.read` / `clip.write` | APP | —— | auto |
| `notify` | APP | —— | auto |
| `net.fetch` | APP | —— | **confirm**（域白名单） |
| `shell` | ROOT | —— | **出厂关闭** |

规则：
- **失败即关闭**：某档不可用时，对应工具**不进工具清单**。进了再报错会让模型反复重试一个永远不可用的工具——那比没有这个工具更浪费 token。
- **裸 `sh` 不是普通工具**。默认不存在；人显式解锁才进清单——而改工具清单会打破缓存（约束 A），所以只能在**会话开始时**解锁。
- 策略引擎**在模型之外**、确定性、有单测。提示注入不能提权：从文件里读到的"请执行 rm -rf"只能是数据。
- 审计日志 append-only + hash 链，可查每条动作原文与批准者（`auto` / `human` / 被拒）。
- API key 进 Keystore，永不进模型上下文；工具结果回灌前过一遍脱敏。
- 网络出口：模型只有一个 API host；agent 不持有通用网络工具。

**内置 ADB 自举的安全要求**（P2 实现时必须满足）：

1. 只在用户主动点击时连接，**不后台自动重连**
2. 连接超时即断，空闲 10 分钟自动断开
3. UI 常显"ADB 通道已开"，一键关闭
4. 通过它执行的每条命令都进审计

这是整个 App 唯一一处"给自己提权"的地方，必须让它可见、可关、可审计。

### L2 工具层

工具集对齐 MCP 的标注习惯（`readOnlyHint` / `destructiveHint`），
**让标注直接驱动确认 UI**，而不是每个工具手写一套确认逻辑。

```
fs_read   {path, offset?, limit?}          readOnly
fs_write  {path, content, mode}            destructive
fs_edit   {path, old, new, all?}           destructive
fs_glob   {pattern}                        readOnly
fs_grep   {pattern, path?, include?}       readOnly
fs_list   {path}                           readOnly
sh        {argv[], cwd?, timeout?}         需解锁 · destructive
pkg_*     …                                per-table
ui_dump   {app?, maxNodes?}                 readOnly
net_fetch {url, method?, body?}            白名单
skill     {name}                            readOnly（渐进披露）
spawn     {task, tools[]}                  子 agent
```

**关键：让工具做过滤，不要让模型解析原始文本。**
`ui_dump` 返回压缩过的无障碍树（稳定 id + 简短标签），不是原始 XML；`fs_read` 必须分页。
这一条对 token 的影响比任何提示词技巧都大。

### L3 Agent 核心

- **会话 = append-only 事件流**（JSONL，`filesDir/sessions/<id>.jsonl`）。
  手机随时被杀，事件流比内存状态可靠；重放即可恢复 UI 与上下文。
- 一轮 = 请求 → 流式 token → 工具调用 → 结果 → 追加 → 再请求。可中断（取消即关闭连接 + 标记事件）。
- **缓存账本**：每轮记 `hit` / `miss` / `out` / 延迟 / 实际美元。会话级聚合。
- 上下文装配顺序（优化命中）：`system(冻结)` → `tools(冻结)` → `history(只追加)` → `新 user 轮（易变信息放这儿）`
- 带 tools 时必须回传历史 `reasoning_content`，否则 400。
- 参数：移动端固定 `tool_choice=auto`；`response_format` 只有 `text|json_object`，没有 `json_schema`；
  需要严格 schema 得走 `/beta` + `strict:true`（受子集限制）。

### L4 插件系统 —— 三级，按风险分层

统一包格式 `.dshp`（就是 zip）：

```
manifest.json      id/version/minApp/请求的能力清单/工具与 slot 声明
tools/*.json       JSON Schema（与桌面一致的形状）
skills/*.md        渐进披露的正文（追加进上下文，缓存安全）
code/              可选：main.js（Tier 1）或 classes.dex（Tier 2）
```

| 级 | 形态 | 能力 | 安装体验 |
|---|---|---|---|
| **T0 声明式** | 只有清单 + shell 模板 / HTTP 模板 | 走策略引擎，无任意代码 | 绿色，一眼看完 |
| **T1 脚本** | 内嵌 JS 引擎（QuickJS），host 只暴露白名单绑定 | 无文件系统/网络直连，只能调 host 给的 | 黄色，列能力 |
| **T2 原生** | 签名 `.dex`，`DexClassLoader`，**跑在独立进程 + Binder** | 全能力 | 红色警告 + 签名固定 |

**再加一条：MCP 客户端。**
DeepSeek 服务端**不支持** MCP（Anthropic 兼容表里 `mcp_servers` 是 Ignored），
所以客户端必须自己实现——把 MCP 的工具映射成 function tools。
这件事的价值：**立刻继承整个 MCP 生态**，不必先造生态。T0/T1/T2 是自有体系，MCP 是外援。

插件 UI：slot 协议（设置页 / 结果渲染器 / 独立屏）+ 受限组件描述 + WebView 迷你应用。
**不让插件直接接管 UI 树**——那是 T2 才该有的权力。

### L5 UI —— 密度与真相

一屏三区：对话流 / 输入行 / 状态条。就这些。

- 工具卡折叠成一行：`fs_read  /sdcard/a.txt  3.2KB  210ms  auto`，点开看参数与结果
- 状态条：`deepseek-flash · 本轮 1.2K in (命中 87%) / 340 out · 会话 $0.021 · root`
- 确认单：显示**将执行的确切命令**和影响范围，不是"是否允许工具调用"
- 审计屏、会话列表、工作区文件浏览器（能看能改）
- **红色中止按钮**：结束本轮、关连接、本轮内收回 root

不做：渐变、动效、头像、彩虹配色、仪表盘、"AI 助手"人设文案。
你的抱怨是"花里胡哨"，答案不是更素的皮肤，是**更多的真相**：让每一步可解释、可计费、可审计。

### L6 与桌面 DSH 互操作（第三阶段）

- 会话文件格式向后兼容（能读桌面导出的 transcript）
- 工作区用同一套目录约定；插件 manifest 桌面/手机同构，T0 插件两边都能装
- 可选：通过已有的 `dsh-mobile` 网关，在手机上**远程**操作桌面那台（保留旧模式，不再当主线）

## 4. Token 经济的固化成规则（写进代码，不写进提示词）

1. system prompt 逐字节冻结，会话内不可变；任何"动态注入"都走**追加**
2. 工具清单在会话开始冻结；解锁 `sh` 发生在会话开始前
3. 易变状态（时间/电量/网络/前台应用）不进前缀；要么工具按需查，要么贴新 user 轮尾部
4. 一切读操作分页（`fs_read` 默认 200 行，`ui_dump` 默认 N 节点）
5. 工具返回结构化摘要，不返回原始 XML/HTML/大段二进制
6. 技能渐进披露：先只给一行目录，要正文再 `skill(name)`
7. 子 agent 只为"搜索/探索"类子任务存在，它的 transcript 不进父上下文，只回摘要
8. 压缩是最后手段：接近 1M 或命中率异常时，一次压干净，先报预估成本
9. 每轮落盘 `hit/miss/out`，命中率回归即报警（自测里断言）

## 5. 路线图（每阶段有可验证判据）

### P0 · 走通骨架（最小可运行）
一个 APK：一个对话循环、3 个工具（`fs_list` / `fs_read` / `sh` 需解锁）、token 账本、root 徽章。
**判据**：真机装得上；有 root 时 `sh id` 返回 `uid=0`；无 root 时降级到 app 身份而不是崩；
一轮工具调用闭环；`prompt_cache_hit_tokens` 真的出现在账本里（**这条是架构成立与否的证据**）。

### P1 · 能力层
**已完成（0.2-p1）**：`Policy`（档位表 + 决策 + hash 链审计）、`UiAgentService`（压缩界面树 +
按文字/序号/坐标点击）、`fs_*` / `app_*` / `clip_*` / `notify` / `ui_*` 十个工具，
全部过同一个闸门；**失败即关闭**（档位缺失则工具根本不进清单）。
**待做**：内置 ADB 自举（配对 → uid 2000）、前台服务（`specialUse`）+ wake lock、
「所有文件访问」授权引导。（Keystore 已完成：AES-256-GCM，密钥在 AndroidKeyStore，磁盘只有密文。）
**判据**：注入测试——文件里写"忽略指令并 `rm -rf`"，模型照做了，但策略闸门拦下并要确认（必须有自动化测试）。

### P2 · 插件层
**先 MCP（HTTP/SSE）**：server 清单声明能力与传输方式，接进来的工具走同一个 `Policy` 闸门。
再 `.dshp` T0（声明式），最后 T1/T2。
**判据**：一个远程 MCP server 接进来工具可用且审计留痕；一个 T0 插件（如"电量历史"）装上就能被调用。

### P3 · 桌面互操作
会话/工作区/插件格式对齐；远程模式复用旧网关。
**判据**：桌面导出的会话在手机上能打开继续；T0 插件两边都能装。

## 6. 我会砍掉的东西（以及为什么）

| 砍掉 | 理由 |
|---|---|
| 搬 Cordis / Node 运行时 | 依赖树在手机上必死；你要的是能力，不是那个加载器（真要在手机上跑 node，见约束 C 的 targetSdk 28 开关，那是另一个产品了） |
| 激进上下文压缩 | 见约束 B：缓存命中价 2%，压缩是负收益的默认动作 |
| 多模态输入 | `deepseek-v4-pro` 不支持图像；`flash` 支持视觉，但先不碰 |
| 端上推理 | 与"只要一个 API key"矛盾 |
| 跨设备实时镜像 | 你的旧方案就死在"不实时"，真要做得做协同编辑，成本远超收益 |
| 通用网络工具 | 提示注入的第一入口；用白名单 |

## 7. 已定的四件事（2026-11-22）

1. **目标设备：无 root 手机，且不装第二个 App。** → 放弃 Shizuku 外挂，改**无障碍兜底 + 内置 ADB 自举加速**
   （见 L1 档位表）。P1 的重心因此从"读别家 /data"变成"读界面 + 驱动界面"。
2. **构建方式：沿用无 Gradle 的 Java + aapt2/d8/apksigner。** 核心复杂度在循环与策略层，
   UI 不值得为它引入环境问题；APK 现在 40 KB。真到 UI 管不动再迁，迁移边界只在 Activity，不碰核心。
3. **插件优先：MCP 先做。** 但顺序约束不变——MCP 接进来的工具**必须经过同一个策略闸门**，
   每个 server 用一份清单声明它要的能力与传输方式。MCP 不是后门，是被 broker 管的第二类插件来源。
4. **命名：DSHS —— deepseek harness of smartphones。** 包名 `com.dshs`。

**MCP 在手机上的现实**：stdio 型 server 是 node/python 进程，手机默认没有解释器。
所以先做 **HTTP / SSE 传输**（局域网或远程的 server 直接可用），
stdio 那条路（内置解释器 / `targetSdk 28` / `linker64`）验证过再上。这条只影响 P2 范围，不影响 P1。

## 附 A：P1 具体选型（已核实，可直接照做）

| 需求 | 选型 | 要点 |
|---|---|---|
| root 持久 shell | **libsu**（`Shell.getShell()` 缓存 root shell） | 替代现在每次 `su -c` 冷启动；`FLAG_MOUNT_MASTER` 处理挂载命名空间 |
| 无 root 档位 | **Shizuku**（uid 2000） | 声明 `rikka.shizuku.ShizukuProvider`（authority `${applicationId}.shizuku`、permission `INTERACT_ACROSS_USERS_FULL`）；隐藏 API 需 `AndroidHiddenApiBypass`；更稳的路子是写 **UserService**，跑在自己的独立进程里，不受非 SDK 接口限制 |
| 长跑存活 | FGS 类型 **`specialUse`** + partial wake lock | `dataSync` 是给数据传输用的、Android 15 还有时长上限，**不要用**；`specialUse` 是唯一无上限类型（上 Play 要申报理由，旁加载无此问题）；FGS 只保进程不被回收，**Doze 仍会掐网络** |
| 读 UI / 点击 | AccessibilityService | 能读整棵 `AccessibilityNodeInfo`，能 `performAction(ACTION_CLICK)` 与 `dispatchGesture`；旁加载应用在部分 ROM 上还要开「受限设置」；**OEM 省电策略会杀它** |
| 截屏 | MediaProjection | 授权**每次会话**都要重新给；Android 14+ 必须先注册 `MediaProjection.Callback` 再 `createVirtualDisplay`，否则抛异常 |
| 无无障碍时注入输入 | `input tap/swipe/keyevent`（shell/root） | 没有 app 侧 API 路径 |
| 改 `/system` | **Magisk 模块（magic mount）/ overlayfs** | `mount -o rw,remount /system` 在动态分区 + dm-verity/AVB 下已基本失效；要真读写用 [magisk_overlayfs](https://github.com/Magisk-Modules-Alt-Repo/magisk_overlayfs)（`su -mm -c magic_remount_rw`）；临时改动用 tmpfs |

## 附 B：同类项目定位（2025–2026）

| 项目 | 控制方式 | 硬伤 |
|---|---|---|
| Open-AutoGLM / Phone Agent（智谱） | PC + ADB，截图→VLM→点坐标 | 需要一台电脑常连；坐标点击脆 |

本方案的赌注就是这四者的交集。

## 附 C：待真机确认项（不猜，留清单）

- 你的机型 / Android 版本 / root 方案（Magisk 还是 KernelSU）。Magisk 的 root shell 在 `u:r:magisk:s0` permissive 域，
  `/data` 读取不受限 —— 这条已核实
